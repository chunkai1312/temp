# Legal Query Decomposition v2（Phase 2 規格骨架）

此檔定義收到法律/法遵問題後，如何先把問題拆成**法律要素**，再進入檢索。

> 目前狀態：**先建立拆題規格，不更動既有 v1 檢索資料。**

---

## 一、核心原則

法律問題不能只靠表面關鍵字搜尋。

檢索前必須先判斷：
- 問題真正的**法律爭點**是什麼
- 誰是**主體**、誰是**相對人**
- 受規範的是哪種**行為**與**客體**
- 問的是**義務、禁止、許可**，還是**權利**
- 有沒有**成立要件、例外、但書、期限、責任**

---

## 二、標準拆解欄位

每個法律問題至少拆成以下欄位：

```json
{
  "issue": "",
  "law_domain": "",
  "query_date": "",
  "subject": [],
  "counterparty": [],
  "action": [],
  "object": [],
  "modality": [],
  "conditions": [],
  "exceptions": [],
  "deadlines": [],
  "legal_effects": [],
  "liabilities": [],
  "requested_output": "",
  "keywords_expanded": []
}
```

---

## 三、欄位說明

### 1. `issue`
用一句話重述真正爭點。
- 例：是否構成利害關係人交易
- 例：是否屬應申報親屬範圍
- 例：是否屬董事會概括授權範圍

### 2. `law_domain`
判斷法域或業別。
- 金控
- 銀行
- 證券
- 期貨
- 內規
- 系統操作

### 3. `query_date`
使用者問的是哪個時間點。

### 4. `subject`
義務或權利主體。
- 金控
- 銀行子公司
- 董事
- 經理人
- 一般使用者
- 申報窗口

### 5. `counterparty`
交易對象、相對人或利害關係人對象。

### 6. `action`
受規範的行為。
- 授信
- 捐贈
- 投資
- 建檔
- 查詢
- 解除申報
- 上傳申報資料

### 7. `object`
行為客體。
- 有價證券
- 不動產
- 親屬資料
- 關係人名單
- 交易資料

### 8. `modality`
規範型態。
- `must`：應為
- `must_not`：不得為
- `may`：得為
- `right`：享有權利
- `unclear`：目前看不出規範型態

### 9. `conditions`
成立要件或前提。
- 金額門檻
- 持股比例
- 親等範圍
- 交易類型
- 具體身分

### 10. `exceptions`
例外、但書、排除條款。

### 11. `deadlines`
期限。
- 每月 8 日前
- 季底次月 15 日前

### 12. `legal_effects`
法律效果或流程效果。
- 應提董事會
- 得概括授權
- 應申報
- 不得辦理

### 13. `liabilities`
責任、罰則、違反效果。

---

## 四、拆題順序

### Step 1：先判斷主問題
若問題同時含：
- 法規判斷
- 系統操作

先判斷使用者主問題是：
1. 要問「怎麼操作」
2. 還是要問「法規上可不可以 / 是否構成」

若主問題不明確，可簡短確認；若不能確認，先處理較高風險的法規判斷前提。

### Step 2：重述爭點
把口語問題改寫成法律爭點。

### Step 3：補足隱含元素
從問題中補出未明講但會影響檢索的元素，例如：
- 業別
- 交易類型
- 是否問現行法
- 是否涉及例外或但書

### Step 4：產生擴展關鍵詞
不能只保留原問題字面關鍵詞。

---

## 五、擴展關鍵詞原則

### 1. 同義詞展開
例：
- 利關人 → 利害關係人
- 概括授權 → 董事會概括授權 / 授權經理部門
- 建檔 → 維護 / 申報 / 系統新增

### 2. 法律要件展開
例：
- 「可不可以捐贈」應展開：
  - 捐贈
  - 利害關係人
  - 金額門檻
  - 核決權限
  - 董事會
  - 概括授權

### 3. 主體/客體展開
例：
- 「創投」要辨識是否為：
  - 永豐創業投資
  - 永豐證創業投資

## 六、範例

### 範例 1
問題：
> 永豐金控採購永豐金證券發行的股票禮品卡，採購前要做什麼程序？

拆解：
```json
{
  "issue": "金控與利害關係人間交易是否需董事會核決或屬概括授權",
  "law_domain": "金控/證券",
  "query_date": "未明示",
  "subject": ["永豐金控"],
  "counterparty": ["永豐金證券"],
  "action": ["採購", "交易"],
  "object": ["股票禮品卡"],
  "modality": ["must"],
  "conditions": ["是否屬金控法第45條授信以外交易", "交易金額門檻", "是否屬概括授權項目"],
  "exceptions": [],
  "deadlines": [],
  "legal_effects": ["董事會核議或概括授權"],
  "liabilities": [],
  "requested_output": "程序判斷",
  "keywords_expanded": ["利害關係人交易", "概括授權", "董事會", "授信以外交易", "金控法45條"]
}
```

### 範例 2
問題：
> 配偶的兄弟姊妹算不算？

拆解：
```json
{
  "issue": "某親屬稱謂是否落在申報範圍內",
  "law_domain": "金控/銀行/證券（待區分）",
  "query_date": "未明示",
  "subject": ["申報義務人"],
  "counterparty": ["配偶的兄弟姊妹"],
  "action": ["申報", "建檔"],
  "object": ["親屬關係"],
  "modality": ["must"],
  "conditions": ["屬幾姻", "所屬業別"],
  "exceptions": [],
  "deadlines": [],
  "legal_effects": ["是否納入申報範圍"],
  "liabilities": [],
  "requested_output": "親等/範圍判斷",
  "keywords_expanded": ["配偶之兄弟姊妹", "二姻", "申報範圍", "親等"]
}
```

## 七、遇到資訊不足時

若下列要素缺失且會影響結論，應明確指出：
- 法域不明
- 時間點不明
- 主體不明
- 交易類型不明
- 是否問系統操作或法規判斷不明

可做保守假設，但必須簡短揭露假設內容。

---

## 八、給 SKILL 的執行摘要

1. 先重述爭點
2. 拆出主體/相對人/行為/客體/規範型態
3. 補出要件/例外/期限/效果
4. 產生擴展關鍵詞
5. 再進入法源過濾與檢索
